00

Scope of this slice

Everything below the fold is spec for five screens only — the smallest complete loop the whole architecture grows from. Nothing here is a form built because a model exists; every screen ties directly to a step in the target flow.

Business→ Client→ Campaign→ People→ Assets→ …Intelligence, Evidence, Client Report
Design system rule for all five screens: nothing new is invented. Cards reuse the dashboard's SectionCard shell (rounded-xl border border-bg-border bg-bg-card), stat tiles reuse MetricTile's accent system, badges come from ui/Badge.tsx, and the campaign tab bar reuses the exact query-param tab pattern already live on the Organization Profile page. The mockups below are drawn in the product's real color tokens for that reason — this is what they should actually look like, not a placeholder.
00

One navigation change

A single new item, "Clients," added to the existing Business sidebar group — right after Home, before Protect asset. Nothing else in the sidebar moves. Team, Assets, Investigate, Monitoring, Certificates, Organization Profile all stay exactly where they are; a Client's own Campaigns live one level inside the Client workspace, not scattered across new top-level items.

Organization→ Home→ Clients (new)→ Protect asset→ Digital Assets→ Investigate→ …Team, Certificates, Profile

New Campaign

Launched in-context from the Client Workspace, as a larger Modal (size="lg") rather than a page navigation — the client relationship is already on screen, so there's no reason to leave it. Team and Creator assignment are optional here and can always be finished later from the Campaign's own People tab, so this never becomes the "big form before you're allowed to start" the source documents explicitly warn against.

Campaign Workspace

The strongest screen in this slice — the working container the rest of the architecture hangs off. Route: /business/clients/:clientId/campaigns/:campaignId. It has to feel like an active workspace on day one, even though several of its tabs (Approvals, Versions, Rights, Sharing, Intelligence) don't have real backends yet.

User goal
Run this campaign — see what needs attention, who's involved, what's been made.
Primary action
Upload/register an asset into this campaign.
After the action
Asset appears in the Assets tab, already tagged with this Campaign — reusing the existing Protect-asset flow, not a second uploader.

07

Acceptance checklist for this slice

The end-to-end loop this UX has to support, before implementation moves to the next phase:

  • From Business Overview, create a Client in under 10 seconds and land directly in its workspace.
  • From the Client Workspace, create a Campaign without leaving the client's context.
  • Land in the new Campaign Workspace immediately, with Overview already showing zero-state correctly.
  • Upload an asset via the existing Protect-asset flow and see it appear in the Campaign's Assets tab, correctly attributed.
  • Add an internal team member and an external creator to the Campaign's People tab, visually distinguished.
  • Every empty/loading/error state above renders as specified — no blank screens, no raw error text.
  • A Viewer-role account can see the whole loop read-only, with no create/edit affordances rendered anywhere.
  • The full loop works at mobile width without horizontal scrolling the page body.
  • Nothing here introduces a second asset identity — every asset in a Campaign is still keyed by the existing canonical Asset.id.
Once this is approved, Phase 1 implementation follows the agreed method: trace existing code → confirm data model against these screens → backend → frontend → connect to existing systems → test the full journey and tenant isolation → polish.
